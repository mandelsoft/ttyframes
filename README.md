# Checking the Behaviour of Animated Terminal Output

`ttyframes` records and checks the behaviour of programs updating trailing
lines of a terminal, for example progress indicators like the examples of
[github.com/mandelsoft/ttyprogress](https://github.com/mandelsoft/ttyprogress).

The design decisions are described in [DESIGN.md](DESIGN.md).

## Why a Tool?

The output of such programs cannot be compared with an expected output byte by
byte. It depends on the timing: how often a line is redrawn, which values are shown
in a frame (elapsed times, percentages) and how independently updated elements are
combined differs from run to run. Additionally, the same screen content can be
generated by different escape sequences. Comparing only the final screen is not
sufficient either, because many changes only show up during the animation.
For example, a progress bar losing the color of a part of its line while it is
running shows the correct final screen.

`ttyframes` therefore compares what is visible on the terminal during the
animation, and it classifies the differences: differences, which can be explained
by the timing, are distinguished from differences indicating a changed behaviour.

## How it Works

1. The main packages are built and run in a pseudo terminal (several runs per package).
2. The output is fed into a line based terminal emulation, which keeps the text
   and the output format of every character.
3. The output is split into *frames*: the screen content before every redraw.
4. Every line of a frame is a *state*, described by its text and its output
   formats. Timing dependent values are masked (by default elapsed seconds `12s`
   and percentages `30%`, shown as `Ns` and `N%`).
5. The *behaviour* of a package is the set of states of all frames of all runs and the
   *transitions* of the lines between consecutive frames.

## Usage

```
ttyframes record [options] <packages>
ttyframes check [options] <packages>
```

`record` stores the behaviour of every main package matching the
[package patterns](https://pkg.go.dev/cmd/go#hdr-Package_lists_and_patterns)
in the file `expected.ttyframes.json` in the package directory. These files are
committed together with the packages. `check` compares the actual behaviour
with the stored one and reports a category per package:

| Category | Meaning | Failure |
|----------|---------|---------|
| `SAME`     | identical states and transitions | no |
| `TIMING`   | identical after normalizing white space, for example columns shifted by values of other lengths | no |
| `SAMPLING` | the same line segments (texts with output format), only in other combinations or with other transitions | no |
| `VALUES`   | the same line segments up to the values of numbers, for example random values chosen by the program | no (with `-strict`: yes) |
| `FORMAT`   | identical texts (up to the values of numbers) with other output formats | yes |
| `TEXT`     | missing or additional texts | yes |
| `MISSING`  | no file with the expected behaviour | yes |
| `ERROR`    | the package could not be built or run | yes |

For `VALUES` and failures, the differing states are reported:

```
FORMAT    examples/progress/linebar: frames 520,521,519/521,520,522, states 22/22 (only expected 8, only actual 8), ...
          format of "Downloading...    Ns   N% (325 KB/500 KB)"
            expected 0:rev=7 26:fg=32
            actual   0:rev=7 26:-
```

The runs of a line are given as character positions followed by the output format
starting there (`-` is the terminal default, `fg=32` the foreground color code 32,
`rev=7` reverse video).

`check` exits with code 1, if there is any failure.

Programs often use random values, for example to simulate the duration of
tasks. If several goroutines share a random number generator, even a fixed seed
does not determine which task gets which value. Such differences are reported as
`VALUES`: the lines are identical up to the values of numbers. With the option
`-strict`, they are failures, for programs whose numbers must be reproducible.

Options:

| Option | Default | Meaning |
|--------|---------|---------|
| `-runs n` | 3 | number of runs per package, their behaviour is merged |
| `-file name` | `expected.ttyframes.json` | name of the file with the expected behaviour |
| `-parallel n` | 4 | number of packages processed in parallel |
| `-mask regexp=replacement` | | additional mask for timing dependent values (repeatable) |
| `-env NAME=value` | | additional environment variable for the runs (repeatable) |
| `-cols n`, `-rows n` | 160, 50 | size of the pseudo terminal |
| `-timeout d` | 3m | maximum duration of a run |
| `-details n` | 10 | maximum number of differing states reported per package |
| `-v` | | report the differing states for all categories |
| `-strict` | | differences of the values of numbers (`VALUES`) are failures |

## Using it in a Project

The tool can be pinned as a tool dependency of a module. With Go 1.23, this is
done with a file `tools.go`, for example in the root directory of the module
(using the package name of this directory):

```golang
//go:build tools

package mymodule

import _ "github.com/mandelsoft/ttyframes/cmd/ttyframes"
```

The build tag excludes the file from normal builds, but `go mod tidy` keeps the
dependency, so that its version is pinned by `go.mod`.

and Makefile targets like

```make
TTYFRAMES := go run github.com/mandelsoft/ttyframes/cmd/ttyframes

behaviour:
	$(TTYFRAMES) record ./examples/...

check-behaviour:
	$(TTYFRAMES) check ./examples/...
```

## The Behaviour File

The behaviour is stored as JSON, so that it can be evaluated by other tools.
The tool writes every state and every transition in a line of its own, so that
changes can be reviewed with `git diff`:

```json
{
  "format": "ttyframes/v1",
  "frames": [520,521,519],
  "states": [
    {"text":"Downloading...    Ns   N% (100 KB/500 KB)","runs":[{"start":0,"format":{"rev":"7"}},{"start":8},{"start":26,"format":{"fg":"32"}}]}
  ],
  "transitions": [
    {"from":{"text":"Downloading...    Ns   N% (75 KB/500 KB)","runs":[...]},"to":{"text":"Downloading...    Ns   N% (100 KB/500 KB)","runs":[...]}}
  ]
}
```

- `format` identifies the file format and its version.
- `frames` are the numbers of frames of the recorded runs (informational only).
- `states` are the lines of all frames: their text and their `runs`, the output formats
  starting at a character position. A `format` gives the codes of the output format areas
  set there (`hl` highlight, `it` italic, `ul` underline, `bl` blinking, `rev` reverse,
  `inv` invisible, `st` strike through, `ol` overline, `fg`, `bg` and `ulc` foreground,
  background and underline color), it is omitted for the terminal default.
- `transitions` are the changes of a line between consecutive frames.

States and transitions are sorted. Any valid JSON with this structure is accepted,
for example a reformatted file. For example, all lines with a green part:

```
jq -r '.states[] | select(any(.runs[]; .format.fg == "32")) | .text' expected.ttyframes.json
```

## Requirements and Limitations

- The pseudo terminal is provided by the command `script` of
  [util-linux](https://github.com/util-linux/util-linux) (Linux).
- The random number generators of `math/rand` use a fixed seed
  (`GODEBUG=randautoseed=0`), so that the runs use the same random values.
  This is not possible for `math/rand/v2`, and it does not determine the values
  of goroutines sharing a generator. Programs using random values typically show
  `SAMPLING`, `TIMING` or `VALUES` differences.
- The terminal emulation is line based: it supports the escape sequences used to
  update trailing lines (cursor movements, erasing lines, output formats).
  Other escape sequences are ignored.
- The classification is a heuristic. In rare cases, an unlucky sampling may be
  reported as `FORMAT`. Recording and checking several runs reduces this effect.
